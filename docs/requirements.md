# Client RAG Demo — v1 Requirements

Working spec for the first version of the app.

## Purpose

A demo RAG (retrieval-augmented generation) chat application: authenticated users upload documents into a shared knowledge base, then chat with an LLM whose answers are grounded in that content. "Client" in the app name refers to the group this demo is being built for, not per-customer data isolation — there is one shared knowledge base for all logged-in users.

## Users & Auth

- Local accounts only, no external IdP.
- Self-registration: any visitor can create an account (username + password).
- No roles — every authenticated user has the same permissions.
- Frontend authenticates to the backend via a session cookie (Spring Security form-login + HttpOnly session), not a bearer token.

## Documents

- Shared knowledge base — every logged-in user can see, chat against, upload, and delete any document. Nothing is scoped to the uploading user.
- Accepted content types: PDF, Word (`.docx`), plain text (`.txt`), all read via `spring-ai-tika-document-reader` (replaces/supplements the PDF-only reader currently in `backend/build.gradle`).
- Re-uploading a file with the same filename **refreshes** that document: its existing chunks/embeddings are replaced, not duplicated. This is an upsert-by-filename on the backend — the frontend already holds the document list (it renders the Documents view from it), so it detects a filename collision locally and shows a confirmation dialog ("This will replace the existing '<name>' — continue?") *before* calling the upload endpoint. The backend itself doesn't need a separate confirm round-trip; it always upserts by filename. Known gap: if two users upload the same filename at nearly the same moment, the second one wins with no server-side conflict detection — acceptable for a demo, not addressed in v1.
- Ingestion (chunking + embedding into pgvector) runs **asynchronously** on a virtual thread (no external job queue needed at this scale). Upload returns immediately with the document in a `PROCESSING` state; the background task embeds it and flips the state to `READY` or `FAILED` (with an error message on failure). The frontend polls the document list while anything is `PROCESSING`.
- No hard cap on total documents — the backend accepts as many as it can process. The "max 10 at a time" rule is a **frontend-only** guard on how many uploads it will keep in flight (queued/processing) simultaneously, to avoid bursting the backend/local Ollama embedding model with a large batch at once. It is not a document-count ceiling, and once in-flight uploads finish, more can start.
- Deletion is supported — any user can delete any document, which removes its chunks/embeddings from pgvector too.

## Chat

- Each user maintains their own list of named chat sessions (like a chat history sidebar), not a single ever-growing thread.
- A session's title is auto-generated by asking the LLM to summarize the first user message, similar to ChatGPT. Shows as "New chat" until that first message lands.
- All chat sessions are grounded against the same shared document knowledge base via the pgvector RAG advisor.
- Each assistant answer includes its **sources** — the document(s)/chunks it was retrieved from — so users can verify answers against real content. Sources are persisted (`chat_message_citations`, keyed to the exact stored message via its Spring-AI-assigned timestamp) and reappear when a session's history is reloaded, not just live during the original streamed response.
- Chat history persists via `spring-ai-starter-model-chat-memory-repository-jdbc`, keyed by chat session id as the conversation id.
- Assistant responses **stream** token-by-token (SSE) rather than waiting for the full answer.
- No delete/archive of chat sessions in v1 — explicitly deferred.
- **Known limitation, partially addressed**: Spring AI's `ChatMemory` (`MessageWindowChatMemory`) keeps only the most recent N messages per conversation, deleting older ones from the database outright once the window advances rather than just hiding them from view — Spring AI hardcodes N=20 (~10 exchanges) with no property to change it. The window size is now externalized as `app.chat.memory.max-messages` (default 20, same as before) via a `ChatMemoryProperties` `@ConfigurationProperties` record injected into a custom `ChatMemory` bean in `ChatConfiguration` — Spring Boot's `@ConditionalOnMissingBean` on Spring AI's own bean is the supported override point. Raising the number is now a config change, not a code change. Still not addressed: eviction still deletes rather than summarizing/archiving, so a long enough conversation still silently loses its early history — just at whatever limit is configured instead of a fixed 20.

## Out of scope for v1

- Per-client / per-tenant data isolation.
- Roles or permission tiers.
- Chat session delete/archive.
- External IdP / SSO.
- Backend-enforced document count limits.
- Responsive/mobile layout (desktop-first; revisit later).
- Visual branding/identity (clean minimal UI for now; decide look later).

## Data model (draft)

Exact column types/constraints will firm up during implementation; this is the shape.

**`users`**
`id`, `username` (unique), `password_hash`, `created_at`

**`documents`**
`id`, `filename` (unique — identity for the refresh-by-filename upsert), `content_type`, `status` (`PROCESSING` / `READY` / `FAILED`), `error_message` (nullable), `chunk_count` (nullable until processed), `uploaded_by` → `users.id` (last user to upload/refresh it), `created_at`, `updated_at`

**`chat_sessions`**
`id`, `owner_username` (denormalized, like `documents.uploaded_by` — keeps the chat feature from taking a DB-level dependency on the users feature's internals), `title` (nullable until auto-generated), `created_at`, `updated_at`

**pgvector `vector_store`** (owned by `spring-ai-starter-vector-store-pgvector`)
Standard `id`/`content`/`metadata`/`embedding` columns; each chunk's `metadata` carries `document_id` and `filename` so a document's chunks can be found and deleted on refresh/delete, and so a retrieved chunk can be traced back to its source document for citations.

**`SPRING_AI_CHAT_MEMORY`** (owned by `spring-ai-model-chat-memory-repository-jdbc`, conversation id = chat session id)
Chat *messages* themselves live here, not in `chat_sessions` — that table holds the title/owner/timestamps around a session, not its messages. Read via Spring AI's `ChatMemory` bean, not a repository we wrote.

**`chat_message_citations`**
`id`, `session_id`, `message_timestamp` (the exact `SPRING_AI_CHAT_MEMORY` row timestamp of the assistant message these citations belong to — join key, not a separate message id we own), `document_id`, `filename`, `created_at`

## API (draft)

**Auth**
- `POST /api/auth/register` `{username, password}`
- `POST /api/auth/login` `{username, password}` → sets session cookie
- `POST /api/auth/logout`
- `GET /api/auth/me`

**Documents**
- `GET /api/documents` — list all (name, status, uploadedBy, updatedAt, chunkCount)
- `POST /api/documents` — multipart upload; upserts by filename; returns the document resource in `PROCESSING`
- `GET /api/documents/{id}` — single-document status (for polling)
- `DELETE /api/documents/{id}`

**Chat**
- `GET /api/chats` — current user's sessions (id, title, updatedAt)
- `POST /api/chats` — create a new session
- `GET /api/chats/{id}/messages` — history for a session, each assistant message including its persisted citations
- `POST /api/chats/{id}/messages` — send a message; SSE stream of assistant tokens, with sources attached at the end of the stream

## User interface

Single-page app, one cohesive shell after login (not separate top-level pages):

- **Login / Register** — simple centered-card forms, minimal styling.
- **App shell**, once authenticated:
  - **Left sidebar**: "New chat" button, the user's chat sessions listed most-recent-first (active one highlighted), a pinned "Documents" nav entry, and a user menu (username, logout) at the bottom.
  - **Main pane** shows one of:
    - **Chat view** — message thread (user/assistant), assistant messages stream in and show an expandable "Sources" list of grounding documents, input box + send button pinned at the bottom.
    - **Documents view** — list/table of documents (filename, status badge, uploaded-by, updated-at, per-row delete), an upload control (drag-and-drop area + browse button) above it. Status badges: amber/spinner for `PROCESSING`, green check for `READY`, red for `FAILED`. The frontend disables/queues new uploads once 10 are in flight, per the concurrency guard above.
- Desktop-first for now; no responsive breakpoints yet.
- Clean, minimal, professional look with no established color/brand identity yet — revisit once the app works end-to-end.

## Remaining open items (implementation-level, low-stakes)

- Retry behavior for a `FAILED` document — currently re-upload only (raw file bytes aren't persisted anywhere after processing, so there's no server-side "retry" action; re-uploading the same filename re-triggers ingestion via the normal refresh path).
- Exact polling interval for document status vs. moving to SSE/WebSocket later if polling feels laggy.

Resolved during implementation: chunking uses Spring AI's `TokenTextSplitter`, chunk size externalized via `app.documents.ingestion.chunk-size` (`DocumentIngestionProperties`, default 800 matching the splitter's own built-in default) - added after a production deployment's embedding model (Tanzu Platform's genai-service proxy serving `nomic-embed-text-v2-moe`, 512-token limit) rejected chunks sized under the default; password hashing is BCrypt via Spring Security's `PasswordEncoder`; all three content types (PDF, DOCX, TXT) go through one `spring-ai-tika-document-reader`-based reader — its bundled Tika standard-parsers package covers PDF and Microsoft Office formats on its own, so the earlier PDF-specific reader was removed as redundant rather than kept alongside it.
